## 2. Case Study A: `Elevator.scxml` & Runtime Event Payloads (`_event.data`)

### 2.1 Structure of `Elevator.scxml`
`Elevator.scxml` models an elevator controller with two `<data>` variables (`currentFloor = 0`, `destination = 0`) and three atomic leaf states inside `main`: `Idle`, `GoingUp`, and `GoingDown`:

```xml
<state id="Idle">
  <transition event="submit" cond="_event.data &gt; currentFloor" target="GoingUp">
    <assign location="destination" expr="_event.data"/>
  </transition>
  <transition event="submit" cond="_event.data &lt; currentFloor" target="GoingDown">
    <assign location="destination" expr="_event.data"/>
  </transition>
</state>
```

Inside `GoingUp` (and `GoingDown`), an eventless (`event=nil`) loop increments `currentFloor = currentFloor + 1` while `currentFloor < destination`, and transitions back to `Idle` when `currentFloor == destination`.

### 2.2 What Happens During Static Flattening
1. **Variable Domain Inference**:
   - The compiler sees `currentFloor` and `destination` initialized to `0` and incremented/decremented by `1`, inferring domains of size 11 (`99` expanded states across 3 control leaves).
2. **Evaluating `_event.data` at Compile Time**:
   - When the elevator is in `main_Idle__currentFloor_0__destination_0`, `submit` carries a runtime payload `_event.data` that is **external to `<datamodel>`**.
   - `evaluate_condition("_event.data > currentFloor", vars)` returns `:error` (statically indeterminate).
   - `execute_actions` for `destination = _event.data` also returns `:error`, preserving `destination = 0`.
3. **Condition-Qualified Disambiguation (`"event [cond]"`)**:
   - Both transitions from `Idle` are preserved with their guard predicates attached to the event name:
     - `"submit [_event.data > currentFloor]"` $\to$ `main_GoingUp__currentFloor_0__destination_0`
     - `"submit [_event.data < currentFloor]"` $\to$ `main_GoingDown__currentFloor_0__destination_0`
4. **Why Only 3 States Are Reachable**:
   - Because `<assign location="destination" expr="_event.data"/>` cannot statically know which floor the user requested (and therefore preserves `destination = 0`), upon entering `GoingUp__currentFloor_0__destination_0`, the guard `currentFloor < destination` (`0 < 0`) is `false`, while the guard `currentFloor == destination` is `false` (or the upward step `currentFloor + 1` is not enabled).
   - Consequently, BFS reachability pruning keeps exactly **3 reachable states** (`Idle`, `GoingUp`, `GoingDown` at `currentFloor_0__destination_0`) and **4 transitions** with **0 broken targets and 0 non-deterministic states**.

> [!NOTE] Theoretical Insight on `_event.data`
> As analyzed in Session 5 (`bb99249c`) and [[4.2 - Current Limitations & Edge Cases]], fully expanding `Elevator.scxml` across all floor pairs $(c, d) \in \{0..N\}^2$ requires treating `_event.data` as a **quantified input parameter** over a finite floor domain $D_{\text{event}} = \{0..N\}$, splitting `"submit"` into concrete events `"submit_0"`, `"submit_1"`, ..., `"submit_N"`.

## 3. Case Study B: `TrafficLightCtrl.scxml` — Parallel Timers, `.choice_0` & History

### 3.1 Structure of `TrafficLightCtrl.scxml`
`TrafficLightCtrl.scxml` (215 lines) models a complete traffic-light intersection controller with:
- A top-level state `main` switching between `off` and `<parallel id="main">`.
- Two orthogonal regions inside `<parallel id="main">`:
  1. `trafficlight`: Composite state `normal` (`Red`, `Yellow`, `Green`, with shallow `<history id="hist">`) and `interrupted` (`Black`, `Yellow`), plus deep history `main.trafficlight.entry_0`.
  2. `timer`: Composite state `running` (`Green`, `Red`, plus `running.choice_0`) and `disabled`, plus deep history `main.timer.entry_0`.
- Inside `timer_running`, the transient choice state `running.choice_0` routes automatically (`event=nil`) based on which light is active in the sibling `trafficlight` region:
  - `<transition cond="In('Green')" target="Green"/>`
  - `<transition cond="In('Red')" target="Red"/>`

### 3.2 How the Compiler Resolves `TrafficLightCtrl.scxml`
1. **Zero Variable Explosion**:
   - Although `TrafficLightCtrl.scxml` declares 5 `<data>` variables (`Timer_OFF`, `counter`, `greenPeriod`, `redPeriod`, `yellowPeriod`), **none** of them appear as mutable variables in any guard (`cond`).
   - `classify_variables/2` classifies all 5 as **display-only**, reducing the variable expansion factor from $k^5$ to **$1\times$**!
2. **Static `In('Green')` / `In('Red')` Resolution + Choice Collapsing**:
   - In every parallel composite tuple `_root_main__...trafficlight_normal_Green__...timer_running_choice_0`, `evaluate_in_predicates/2` statically resolves `In('Green')` to `true` and `In('Red')` to `false`.
   - `collapse_pseudo_state_chains/3` then collapses the `.choice_0` pseudo-state directly to its resolved target (`timer_running_Green`), eliminating all non-deterministic `_auto` transitions!
3. **Final Metrics**:
   - **Stored Artifact (`2e88cae`)**: **25 states, 130 transitions** (5.20 avg out-degree), **0 broken targets, 0 `null` inputs, 0 dead ends, 0 non-deterministic states**.
   - **Current V3 (with generalized history)**: **21 reachable states** (20 parallel composites + `main_off__`), 100% deterministic.
