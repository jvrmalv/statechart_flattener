## 1. The Synthetic Non-Determinism Problem

After compiling `watch.scxml` in Session 4 (April 4, 2026, commit `8e82cc4`), structural inspection of the 7,040-state output revealed that **4,480 out of 7,040 states (63.6%) had non-deterministic transitions**—i.e., multiple outgoing transitions from the same state triggered by the exact same `input` event!

Similarly, in `TrafficLightCtrl.scxml` and `Elevator.scxml`, multiple transitions shared the same event name from the same state.

Investigation in Session 6 (April 20–28, 2026, commit `2e88cae`) identified **three distinct root causes** of synthetic non-determinism during statechart flattening:

```mermaid
flowchart TD
    ND["Synthetic Non-Determinism<br/>Multiple transitions with same `(state, input)`"] --> RC1["Root Cause 1: Hierarchical Inheritance Without Shadowing<br/>Child state and parent state both define transitions on event `e`"]
    ND --> RC2["Root Cause 2: Same-State Guard Ordering (If / Else-If)<br/>Transition 1 has `cond='C'`, Transition 2 is unconditional fallback on same event `e`"]
    ND --> RC3["Root Cause 3: Unresolvable Runtime Guards (`:error`)<br/>Guards referencing `_event.data` or external functions cannot be decided statically"]
    RC1 & RC2 --> Fix1["Solution A: W3C Inner-First + Document-Order Priority<br/>(`dedup_by_event_priority/1`)"]
    RC3 --> Fix2["Solution B: Condition-Qualified Event Disambiguation<br/>(`input: \"event [cond]\"`)"]
```

## 2. Root Cause 1 & 2: W3C Inner-First and Document-Order Shadowing

According to the **W3C SCXML Specification (§3.13 Selecting and Executing Transitions)**:
1. **Inner-First (Hierarchical) Priority**: If an atomic leaf state $s$ and one of its ancestor composite states $P$ both have enabled transitions on event $e$, the **more deeply nested (innermost) state $s$ takes strict precedence** and shadows the ancestor's transition.
   - *Example in `watch.scxml`*: Composite state `Alarm_1` defines `<transition event="c_button" target="Alarm_2"/>` (depth 3). Inside `Alarm_1`, child state `Alarm_1_set` defines `<transition event="c_button" target="disabled"/>` (depth 4). When the watch is in `Alarm_1_set_hours`, pressing `c_button` must exit `set` to `disabled`—it must **not** also include the shadowed transition to `Alarm_2`!
2. **Document-Order Priority (If / Else-If Chains)**: Within the **same** state element, transitions are evaluated in **XML document order**. A guarded transition `<transition event="e" cond="C" target="T1"/>` followed by an unconditional fallback `<transition event="e" target="T2"/>` represents an `if (C) goto T1 else goto T2` construct.
   - When `C` evaluates to `true` in a specific variable-expanded state $(s, \vec{v})$, **both** the guarded transition (`true`) and the unconditional fallback (`nil`) are enabled! Under W3C semantics, the earlier transition in document order (`T1`) wins and shadows the fallback (`T2`).

### Implementation: `source_depth`, `doc_order`, and `dedup_by_event_priority/1`
To enforce both rules in [lib/scxml_flattener_full.exs](file:////wsl.localhost/Ubuntu-24.04/home/jvrmalv/code/statechart_flattener/lib/scxml_flattener_full.exs):
1. During `get_Trans/2` (Stage 6), every extracted transition is annotated with:
   - `source_depth`: The lexical nesting depth of the `<state>` element on which the `<transition>` was defined (higher = deeper/innermost).
   - `doc_order`: The sequential index of the `<transition>` element within its parent `<state>` (lower = earlier in XML document).
2. After variable expansion and static guard filtering in Stage 7–8, `dedup_by_event_priority/1` ([lib/scxml_flattener_full.exs](file:////wsl.localhost/Ubuntu-24.04/home/jvrmalv/code/statechart_flattener/lib/scxml_flattener_full.exs#L1320-L1343)) groups all statically enabled transitions of a state by their effective event key and selects the highest-priority transition:

$$\text{Priority}(t) = (-\text{source\_depth}(t), \;\; +\text{doc\_order}(t))$$

```elixir
transitions
|> Enum.group_by(&effective_event_key/1)
|> Enum.flat_map(fn {_event_key, group} ->
  # Keep all runtime-guarded transitions (which have distinct [cond] keys),
  # and for statically resolved transitions on the same event, pick the winner
  # by highest source_depth (innermost state), breaking ties by lowest doc_order.
  winner = Enum.min_by(group, fn t ->
    {-Map.get(t, :source_depth, 0), Map.get(t, :doc_order, 0)}
  end)
  [winner]
end)
```

## 3. Root Cause 3: Runtime-Dependent Guards (`:error`) & `"event [cond]"` Disambiguation

What happens when a transition's `cond` attribute **cannot** be evaluated at compile time because it depends on runtime event payloads or external sensors?
- **Example ([statechart_with_integrations/Elevator.scxml](file:////wsl.localhost/Ubuntu-24.04/home/jvrmalv/code/statechart_flattener/statechart_with_integrations/Elevator.scxml))**:
  ```xml
  <state id="Idle">
    <transition event="submit" cond="_event.data &gt; currentFloor" target="GoingUp">
      <assign location="destination" expr="_event.data"/>
    </transition>
    <transition event="submit" cond="_event.data &lt; currentFloor" target="GoingDown">
      <assign location="destination" expr="_event.data"/>
    </transition>
  </state>
  ```
- Here, `_event.data` is the floor number pressed by a passenger at runtime—it is not a state variable in `<datamodel>`.
- When `evaluate_condition/4` evaluates `_event.data > 0`, it returns **`:error`** (meaning *statically indeterminate / runtime-dependent*).

### Why Dropping or Unconditionally Keeping `:error` Guards Both Fail
- If `:error` were treated as `false`, both `submit` transitions would be deleted, trapping `Elevator.scxml` in `Idle` with 0 transitions!
- If `:error` were treated as `true` and stripped, `Idle` would have **two** transitions with `"input": "submit"` (one to `GoingUp`, one to `GoingDown`), which `dedup_by_event_priority/1` would collapse into just `GoingUp` (deleting `GoingDown`!) or leave as an unlabelled non-deterministic branch.

### Solution: Condition-Qualified Event Labels (`"event [cond]"`)
When `evaluate_condition/4` returns `:error`, Stage 7 preserves the transition and marks it with `keep_cond: cond_str`. During serialization (and priority grouping), its input event label is formatted as:

$$\texttt{input} = \begin{cases} \texttt{"}\langle\text{event}\rangle\texttt{ [}\langle\text{cond}\rangle\texttt{]"} & \text{if } \text{eval}(\text{cond}) = \texttt{:error} \\ \texttt{"\_auto [}\langle\text{cond}\rangle\texttt{]"} & \text{if event is nil and } \text{eval}(\text{cond}) = \texttt{:error} \\ \texttt{"}\langle\text{event}\rangle\texttt{"} & \text{if } \text{eval}(\text{cond}) = \texttt{true} \end{cases}$$

For `Elevator.scxml`, `main_Idle__currentFloor_0__destination_0` cleanly emits two distinct, deterministic transitions:
- `"input": "submit [_event.data > currentFloor]"` $\to$ `main_GoingUp__currentFloor_0__destination_0`
- `"input": "submit [_event.data < currentFloor]"` $\to$ `main_GoingDown__currentFloor_0__destination_0`

## 4. Transient Pseudo-State Chain Collapsing (`collapse_pseudo_state_chains/3`)

Itemis CREATE exports entry and choice routing points as transient `<state id="...entry_0">` or `<state id="...choice_0">` elements with eventless (`event=nil`, i.e., `"_auto"`) outgoing transitions.
- In Stage 8, `collapse_pseudo_state_chains/3` ([lib/scxml_flattener_full.exs](file:////wsl.localhost/Ubuntu-24.04/home/jvrmalv/code/statechart_flattener/lib/scxml_flattener_full.exs#L1345-L1391)) computes the $\varepsilon$-closure of any transition targeting a pseudo-state $p \in S_{\text{pseudo}}$:
  1. If $p$ has statically resolved `"_auto"` transitions (without runtime `keep_cond`), the incoming transition $s \xrightarrow{e} p$ bypasses $p$ directly to $p$'s target $t$, concatenating:
     $$\text{actions}(s \to t) = \text{actions}(s \to p) \mathbin{\Vert} \text{onentry}(p) \mathbin{\Vert} \text{onexit}(p) \mathbin{\Vert} \text{actions}(p \to t)$$
  2. Cycle detection (`visited` set) prevents infinite loops on malformed $\varepsilon$-cycles.
