## 1. The Extended Finite-State Machine (EFSM) Explosion Problem

A statechart with `<datamodel>` variables is formally an **Extended Finite-State Machine (EFSM)**. To flatten an EFSM into a pure FSM where guard conditions (`cond="..."`) are statically eliminated, each control state $s \in S_{\text{atomic}}$ must be expanded over the Cartesian product of the domains $D_v$ of its variables $v \in V$:

$$|S_{\text{expanded}}| = |S_{\text{atomic}}| \times \prod_{v \in V} |D_v|$$

### Why Unfiltered Variable Expansion Fails on Real Models
When `lib/scxml_flattener_full.exs` was first applied to [harel_watch/watch.scxml](file:////wsl.localhost/Ubuntu-24.04/home/jvrmalv/code/statechart_flattener/harel_watch/watch.scxml) (commit `4d1e9ee` / `best_to_date_backup.exs`), the compiler froze and exhausted memory:
- `watch.scxml` declares **14 `<data>` variables**:
  `time`, `alarm_1_time`, `alarm_1_enabled`, `alarm_2_time`, `alarm_2_enabled`, `chime_enabled`, `time_set`, `stop_time`, `stop_lap_time`, `stop_display_time`, `display_first`, `display_second`, `display_third`, `display_text`.
- Even if each variable took only 2 values, $64 \times 2^{14} = 1,048,576$ states. With integer domains inferred from literals (`0`, `1`, `30000`, `360000`, `8640000`), the unpruned Cartesian product exceeded **$1.4 \times 10^6$ states**, causing combinatorial collapse.

## 2. Technique 1: Guard-Relevant vs. Display-Only Variable Partitioning (`classify_variables/2`)

The key insight introduced in commit `746143f` ([lib/scxml_flattener_full.exs](file:////wsl.localhost/Ubuntu-24.04/home/jvrmalv/code/statechart_flattener/lib/scxml_flattener_full.exs#L533-L579)) is **Cone-of-Influence (COI) static variable slicing**:

> [!TIP] Theorem: Display-Only Variables Do Not Affect Control Flow
> Let $V_{\text{cond}} \subseteq V$ be the set of variables referenced inside any `<transition cond="...">` attribute across the entire SCXML document, and let $V_{\text{guard}}$ be the transitive closure of variables that flow into $V_{\text{cond}}$ or are mutated and tested in guards.
> Any variable $v \in V \setminus V_{\text{guard}}$ is a **display-only (or constant/output-only) variable**: its value never enables or disables any transition. Therefore, expanding states over $D_v$ creates isomorphic copies of the control graph without changing transition reachability or branching!

`classify_variables/2` scans all `<transition cond="...">`, `<assign>`, and `<script>` expressions and partitions $V$ into:

1. **Guard-Relevant Variables ($V_{\text{guard}}$)**: Variables that appear in at least one `cond` attribute AND are mutated (assigned) in at least one `<assign>` or `<script>`.
2. **Display-Only / Constant Variables ($V_{\text{display}}$)**: Variables that either:
   - Never appear in any `cond` attribute (e.g., `display_first`, `display_text`, `stop_time` in `watch.scxml`; `luminosity_delay`, `motion_timeout` in `_04`; `wait_time` in `_05`), or
   - Appear in `cond` only as **immutable constants** (never modified after `<datamodel>` initialization, e.g., `simulation_WAIT_MIN`, `Timer_OFF`, `greenPeriod` in `TrafficLightCtrl.scxml`). Immutable constants are substituted directly from their initial `<data expr="...">` value during guard evaluation!

### Impact Across Benchmark Models

| Model | Total `<data>` Vars | Guard-Relevant Mutable Vars ($V_{\text{guard}}$) | Display-Only / Constant Vars ($V_{\text{display}}$) | State Space Reduction Factor |
| :--- | :---: | :--- | :--- | :---: |
| **`_04_LightAndMotionSensing`** | 3 | `["brightness"]` (1) | `["luminosity_delay", "motion_timeout"]` (2) | **$4\times$ – $9\times$** |
| **`_05_PresenceSimulation`** | 6 | `["brightness", "hour"]` (2) | `["simulation_UPDATE_PERIOD", "simulation_WAIT_MAX", "simulation_WAIT_MIN", "wait_time"]` (4) | **$16\times$ – $81\times$** |
| **`TrafficLightCtrl.scxml`** | 5 | `[]` (0 — all 5 are constants/counters not in guards) | `["Timer_OFF", "counter", "greenPeriod", "redPeriod", "yellowPeriod"]` (5) | **$32\times+$** (21 states total!) |
| **`watch.scxml`** | 14 | `["alarm_1_enabled", "alarm_1_time", "alarm_2_enabled", "alarm_2_time", "chime_enabled", "time", "time_set"]` (7) | `["display_first", "display_second", "display_text", "display_third", "stop_display_time", "stop_lap_time", "stop_time"]` (7) | **$> 175\times$** ($1.4\text{M} \to 8,192$) |

## 3. Technique 2: Finite Domain Inference & Nearest-Value Snapping (`snap_to_domain/2`)

Even after restricting expansion to $V_{\text{guard}}$, arithmetic operations in actions such as:
- `time = (time + 1) % 8640000` (in `watch.scxml`)
- `alarm_1_time = (alarm_1_time + 6000) % 8640000` (in `watch.scxml`)
- `brightness = brightness + 1` (in `_02`, `_03`, `_04`, `_05`)

would generate millions of intermediate integers ($0, 1, 2, \dots, 8639999$) if evaluated literally, or produce target state IDs that do not exist in the pre-expanded state dictionary (**broken target references**).

### 3.1 How `infer_variable_domains/3` Builds Finite Abstract Domains
For each guard-relevant variable $v \in V_{\text{guard}}$:
1. **Booleans**: If initial value or assignments are `"true"` / `"false"`, the domain is `[false, true]`.
2. **Integers**: Extracts the initial value $v_0$, all integer literals compared against $v$ in guards (`v == c`, `v > c`, `v >= c`, `v < c`, `v <= c`), and boundary witnesses ($c - 1, c, c + 1$ for inequalities):
   - In `watch.scxml`, `time`, `alarm_1_time`, `alarm_2_time`, and `time_set` are only compared for equality (`time == alarm_1_time`, `time % 360000 == 0`, `time_set == 1`). Their inferred abstract domain is **`[0, 1]`** (representing $0$ = baseline/aligned and $1$ = incremented/offset).
   - Thus, all 7 guard variables in `watch.scxml` have binary domains ($|D_v| = 2$), giving $64 \times 2^7 = \mathbf{8,192}$ base expanded states!

### 3.2 How `snap_to_domain/2` Eliminates Out-of-Domain Target States
When a transition action mutates a variable $v \gets \text{val}_{\text{new}}$ (e.g., `alarm_1_time = (0 + 6000) % 8640000 = 6000`), the value `6000` is not in the inferred domain `[0, 1]`.

`snap_to_domain/2` ([lib/scxml_flattener_full.exs](file:////wsl.localhost/Ubuntu-24.04/home/jvrmalv/code/statechart_flattener/lib/scxml_flattener_full.exs#L1290-L1301)) maps any computed numeric result to the **nearest value in the variable's finite domain $D_v$** (with directional awareness so a positive increment from `0` snaps to the smallest positive domain value `1`):

$$\text{snap}(\text{val}_{\text{new}}, D_v) = \arg\min_{d \in D_v} |\text{val}_{\text{new}} - d|$$

- In `watch.scxml`, `0 + 6000 = 6000` snaps to `1` in `[0, 1]`, allowing `time` and `alarm_1_time` to become both `1` (triggering the alarm guard `time == alarm_1_time && alarm_1_enabled`)!

> [!WARNING] Important Trade-off of Nearest-Value Snapping (See [[4.2 - Current Limitations & Edge Cases]])
> While `snap_to_domain/2` is ideal for abstracting large timers (`+ 6000` $\to$ `1`), it introduces a subtle quantization artifact on multi-step counters whose intermediate steps are not mentioned as literals in the SCXML:
> - In `_02_DimmableLightSwitch.scxml`, `brightness` starts at `0`, increments by `brightness = brightness + 1` while `brightness < 10`, and is only mentioned with literals `0`, `1`, `2`, `10`.
> - Under the earlier domain inference (`af06c2f`, stored in `lib/generated_jsons/_02_DimmableLightSwitch_flattened.json`), `brightness` was expanded over the full range `[0..10]` (11 values $\to$ **21 reachable states**).
> - Under `snap_to_domain/2` with literal-only domain `[0, 1, 2, 10]`, incrementing `brightness` from `2` computes `2 + 1 = 3`, which is closer to `2` ($|3-2|=1$) than to `10` ($|3-10|=7$), so it snaps back to `2` (**3 reachable states**)! This trade-off is analyzed in detail in [[3.2 - Progressive LightSwitch Benchmark (_01 to _05)]] and [[4.2 - Current Limitations & Edge Cases]].

## 4. Technique 3: Non-Deterministic External Function Fallback (`:error`)

In models like [_04_LightAndMotionSensingLightSwitch.scxml](file:////wsl.localhost/Ubuntu-24.04/home/jvrmalv/code/statechart_flattener/lib/original_scxml/_04_LightAndMotionSensingLightSwitch.scxml) and [_05_PresenceSimulationLightSwitch.scxml](file:////wsl.localhost/Ubuntu-24.04/home/jvrmalv/code/statechart_flattener/lib/original_scxml/_05_PresenceSimulationLightSwitch.scxml), transition actions call external environment functions that cannot be evaluated statically:
- `<assign location="hour" expr="get_hour()"/>`
- `<assign location="wait_time" expr="get_rand(simulation_WAIT_MIN, simulation_WAIT_MAX)"/>`

### The Bug Prior to Session 3 (March 2026)
Originally, `evaluate_expression("get_hour()", vars)` caught the `CompileError` / `UndefinedFunctionError` and returned **`false`**. That overwrote `hour` with `false`, generating invalid target state IDs like `...__brightness_0__hour_false` that did not exist in the integer-expanded state dictionary (`__hour_0` .. `__hour_23`), causing **242 broken transitions** in `_05`!

### The `:error` Sentinel Fix
`evaluate_expression/3` was updated to return `:error` whenever an expression references an undefined external function or runtime payload (`_event.data`). When `execute_actions/5` receives `:error` for an assignment to variable $v$:
- It **preserves the current value of $v$** from the source state (or branches across the domain when appropriate), guaranteeing that `hour` remains a valid member of $D_{\text{hour}}$ and eliminating all 242 broken transitions.
