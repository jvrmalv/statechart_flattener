## 1. Overview: Theoretical vs. Engineering Limitations

A rigorous engineering audit of [lib/scxml_flattener_full.exs](file:////wsl.localhost/Ubuntu-24.04/home/jvrmalv/code/statechart_flattener/lib/scxml_flattener_full.exs) and its outputs reveals two classes of limitations:
1. **Fundamental Theoretical Boundaries**: Consequences of flattening Turing-complete Extended Finite-State Machines (EFSMs) with unbounded data or external runtime inputs into finite-state automata.
2. **Implementation-Specific Heuristics & Edge Cases**: Design trade-offs in the current Elixir implementation that can affect specific SCXML idioms.

## 2. Limitation 1: Nearest-Value Domain Snapping (`snap_to_domain/2`) Quantization on Multi-Step Counters

### The Mechanism
In [lib/scxml_flattener_full.exs](file:////wsl.localhost/Ubuntu-24.04/home/jvrmalv/code/statechart_flattener/lib/scxml_flattener_full.exs#L581-L678), `infer_variable_domains/3` constructs the finite domain $D_v$ of an integer variable $v$ from its initial value, literals appearing in guards/assignments, and boundary neighbors ($c-1, c, c+1$). When an assignment computes a value outside $D_v$, `snap_to_domain/2` snaps it to the closest element in $D_v$.

### The Edge Case Observed in `_02_DimmableLightSwitch` and `_03_MotionLightSwitch`
- In `_02_DimmableLightSwitch.scxml`, `brightness` is initialized to `0`, assigned `1` on entering `On`, and incremented via `brightness = brightness + 1` under the guard `brightness < 10`.
- The literals extracted for `brightness` are `[0, 1, 2, 10]` (where `2` comes from `1 + 1`, and `10` comes from `< 10` / `>= 10`, with `9` omitted if only literal extraction is active).
- When `brightness = 2` and `brightness = brightness + 1` executes:
  $$\text{val}_{\text{new}} = 2 + 1 = 3$$
- `snap_to_domain(3, [0, 1, 2, 10])` compares $|3 - 2| = 1$ against $|3 - 10| = 7$, and **snaps `3` back down to `2`**!
- **Consequence**: In the live V3 pipeline, `brightness` saturates at `2` and never reaches `10` (producing **3 reachable states** for `_02` instead of the **21 reachable states** in the stored artifact `lib/generated_jsons/_02_DimmableLightSwitch_flattened.json` generated before `snap_to_domain/2` replaced full range `[0..10]` expansion).

> [!TIP] How to Resolve This Trade-off
> As detailed in [[4.3 - Future Work & Research Roadmap]], `snap_to_domain/2` should use **directional (monotonic) snapping** (if $\text{val}_{\text{new}} > \text{val}_{\text{old}}$, snap to the smallest $d \in D_v$ such that $d \ge \text{val}_{\text{new}}$) AND `infer_variable_domains/3` should expand contiguous integer ranges `[min..max]` whenever `max - min <= MAX_RANGE_THRESHOLD` (e.g., $\le 32$), reserving binary/sparse domain snapping for large constants like `8640000` in `watch.scxml`.

## 3. Limitation 2: Runtime Event Payloads (`_event.data`) and External Functions (`get_hour()`, `get_rand()`)

### The Mechanism
When an SCXML guard or assignment references:
- `_event.data` (e.g., `Elevator.scxml`: `cond="_event.data > currentFloor"`, `<assign location="destination" expr="_event.data"/>`), or
- Uninterpreted external C/JS host functions (e.g., `_05_PresenceSimulationLightSwitch.scxml`: `<assign location="hour" expr="get_hour()"/>`),

`evaluate_expression/3` returns `:error`.
- For **guards**, the compiler preserves the transition with a condition-qualified event label (`"submit [_event.data > currentFloor]"`).
- For **assignments**, `execute_actions/5` **keeps the current value of the target variable unchanged** (`destination` stays `0`; `hour` stays `0`).

### The Consequence
- **In `Elevator.scxml`**: Because `destination = _event.data` leaves `destination` at `0`, the elevator enters `GoingUp__currentFloor_0__destination_0` where `currentFloor == destination` (`0 == 0`), so the multi-floor movement states (`currentFloor_1`, `currentFloor_2`, ...) are never reached during static BFS (**99 expanded states $\to$ 3 reachable states**).
- **In `_05_PresenceSimulationLightSwitch.scxml`**: Because `hour = get_hour()` leaves `hour` at its prior value (unless mutated by a literal), transitions that depend on `get_hour()` dynamically changing `hour` from daytime (`12`) to nighttime (`18`) are not explored via `get_hour()` alone.

> [!WARNING] Why Embedding QuickJS / V8 NIFs Does Not Solve This Alone
> In Session 6 (`e1045a47`), we analyzed whether replacing Elixir's `Code.eval_string` with a JavaScript engine NIF (QuickJS or V8) would eliminate `:error` fallbacks.
> **Conclusion**: While a JS engine solves **syntactic ECMAScript compatibility** (bitwise operators, JS string methods), it **cannot** know the runtime return value of an external sensor (`get_hour()`) or future user input (`_event.data`) at compile time! To explore all outcomes of `x = get_hour()` or `destination = _event.data` in a static FSM, the compiler must perform **non-deterministic domain branching**—generating transitions to *all* $d \in D_x$ labeled `"event [x=d]"`.

## 4. Limitation 3: Display-Only Variable Mutation Not Reflected in State IDs

By design, Stage 3 (`classify_variables/2`) excludes display-only variables ($V_{\text{display}}$, i.e., variables that never appear in any `cond` attribute) from the state ID expansion.
- Their `<assign>` and `<script>` mutations are **preserved inside the `onentry`, `onexit`, and `actions` arrays** of the flattened JSON and SCXML.
- However, if a downstream consumer ignores the `actions` array and expects the state ID string alone to encode display-only variables (such as `stop_time` or `display_text` in `watch.scxml`, or `hasProduct` in `test_vending_machine.scxml`), those values are not part of the state name.

## 5. Limitation 4: Regex-Based ECMAScript Expression Translator (`evaluate_expression/3`)

Rather than parsing ECMAScript guards and `<script>` blocks into an Abstract Syntax Tree (AST), `evaluate_expression/3` ([lib/scxml_flattener_full.exs](file:////wsl.localhost/Ubuntu-24.04/home/jvrmalv/code/statechart_flattener/lib/scxml_flattener_full.exs#L1211-L1288)) uses a sequence of regular expression substitutions to translate ECMAScript into Elixir syntax before calling `Code.eval_string/2`:
- `&&` $\to$ `and`, `||` $\to$ `or`, `!` $\to$ `not`
- `%` (modulo) $\to$ `rem(a, b)` via regex `/(\w+|\([^)]+\))\s*%\s*(\w+)/`
- Variable names replaced via word-boundary regex `\bvar_name\b`

### Edge Cases of Regex Translation
1. **Nested Modulo or Complex Parenthesized Expressions**: The modulo regex `(\w+|\([^)]+\))\s*%\s*(\w+)` handles one level of parentheses (such as `(time + 1) % 8640000`), but deeply nested expressions like `((a + b) * (c + d)) % (e + f)` will fail regex matching and fall back to `:error`.
2. **Compound Assignment Operators**: Operators like `+=`, `-=`, `*=`, `++`, `--`, or ternary expressions `cond ? a : b` inside `<script>` blocks are not currently decomposed by `parse_script_assignments/1`.
3. **`Code.eval_string/2` Performance Overhead**: Calling `Code.eval_string/2` hundreds of thousands of times during Stage 7 variable expansion accounts for ~75% of the compilation wall-clock time on `watch.scxml` (~10–12 seconds).

## 6. Limitation 5: Advanced W3C SCXML Constructs Out of Scope

The compiler targets the statechart subset used by Harel Statecharts and itemis CREATE / YAKINDU exports. The following W3C SCXML runtime/distributed features are not supported:
- **Internal Event Queue Raising (`<raise event="..."/>` and `<send event="..." delay="..."/>`)**: Raising internal events inside `onentry`/`onexit` or transition actions that trigger cascading microsteps within the same macrostep.
- **External Service Invocation (`<invoke>`, `<finalize>`, `<donedata>`)**: Spawning external child statecharts or asynchronous actors.
- **Executable Conditional Blocks (`<if>`, `<elseif>`, `<else>`, `<foreach>`)** inside `<onentry>` / `<onexit>` / `<transition>` bodies (guards on `<transition cond="...">` and `.choice_0` pseudo-states *are* supported).
- **Typo in Default SCXML Output Filename**: When invoked with a custom output prefix (`elixir lib/scxml_flattener_full.exs input.scxml out_prefix`), line 198 of `lib/scxml_flattener_full.exs` writes `#{out_prefix}_flatenned.scxml` (with double `n`, single `t`), whereas `watch_flattened.scxml` uses the corrected spelling.
